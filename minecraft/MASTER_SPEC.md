## 第2章 世界観・ストーリー

4人の勇者は、元の世界では普通の大学生だった。

ある日、4人はパラレルワールドに迷い込む。

元の世界では空気のように存在感のなかった野口が、この世界では存在感が反転し、神々すら超越する魔神となっていた。

かつて平和だった世界は魔神野口によって荒廃し、多くの王国や神々が滅ぼされている。

4人は滅亡寸前の富里王国で、女性の王であるホープと出会う。

ホープから、魔神野口を倒せば元の世界に帰れると知らされ、魔王城を目指すことになる。

魔王城へすぐに行けない理由は、単純に非常に遠い場所にあるためとする。特殊な結界や鍵を主要な理由として追加しないこと。

勇者たちは道中で各地の人々を救い、富里王国を復興させ、自分たちも成長していく。

## 第3章 100固定ステージ制

以前のランダムダンジョン生成システムは廃止する。

### 基本仕様

* 事前制作した100個の固定マップを使用する。
* 地形や部屋の構造をランダム生成しない。
* ステージへの移動はテレポート方式とする。
* メインステージはストーリー進行によって順番に解放する。
* クリア済みの戦闘ステージは再挑戦可能とする。
* 攻略後は必ず富里王国へ帰還する。
* 報酬はプレイヤーごとの個別ランダム報酬とする。
* 通常の攻略時間は5～15分程度。
* 高難易度ステージは最大3時間程度まで許容する。
* 長時間ステージでは途中再開や休憩地点を用意する。

### 章構成

10ステージごとに一つの物語を構成する。

* 第1章：ステージ1～10
* 第2章：ステージ11～20
* 第3章：ステージ21～30
* 第4章：ステージ31～40
* 第5章：ステージ41～50
* 第6章：ステージ51～60
* 第7章：ステージ61～70
* 第8章：ステージ71～80
* 第9章：ステージ81～90
* 最終章：ステージ91～100

ステージ10、20、30、40、50、60、70、80、90、100には章を締めくくる大型ボスを配置する。

途中のステージにも中ボスを配置可能とする。

ステージ100は魔神野口との最終決戦とする。

### ステージの攻略方式

ステージごとに異なる攻略方式を設定する。

* 一本道の探索
* 自由探索
* エリア解放
* 魔物討伐
* ボス討伐
* 住民救出
* NPC護衛
* 防衛
* 謎解き
* 生存
* 特殊試練
* 会話・ストーリー進行

すべてのステージを同じ構成にしないこと。

### マップ制作

マップ制作も開発範囲に含める。

プレイヤー自身が100ステージを手作業で建築することを前提にしない。

構造物ファイル、固定の建築データ、スクリプトによる建築など、統合版で実現可能な方式を使用する。

各ステージには固有ID、固定座標、入場地点、帰還地点、敵配置、攻略条件、報酬、再挑戦時のリセット処理を設定できるようにする。

## 第4章 富里王国

富里王国はゲーム全体の中心となる共通ハブである。

### ステージ1開始時

かつて繁栄していた富里王国は、魔神野口の影響によって滅亡寸前となっている。

* 住民はホープ1人のみ。
* 利用可能な施設は宿屋のみ。
* 王国内には魔物が徘徊している。
* 勇者たちはホープと出会う。
* 王国内の魔物をすべて討伐することが最初の攻略目標となる。

### ステージ1攻略後

王国内の魔物をすべて討伐すると、王国のマップが変化する。

城だけが建つ状態から本格的な復興が始まる。

以降、富里王国は全ステージ共通の帰還地点となる。

### 王国復興システム

各ステージを初めてクリアすると、助けた住民が自動的に富里王国へ移住する。

住民の移住に応じて建物が自動建設され、施設が解放される。

同じステージを周回しても住民や建物が重複して増加しないこと。

護衛対象のNPCを守りながら攻略するステージも用意する。

王国は最終的に約100棟の建物を持つ巨大王都へ発展する。

### 解放される施設

* 王城
* 道具屋
* 武器屋
* 防具屋
* 鍛冶場
* 冒険者ギルド
* 転職神殿
* 教会
* 魔法研究所
* 訓練場
* 倉庫
* 図書館
* 宿屋
* 試練の神殿
* 民家
* 兵舎
* その他の特殊施設

施設の具体的な解放順はストーリー制作時に設定する。

勇者専用の個人拠点や自由建築による拠点発展は実装しない。

* 種族：人間
* レベル：1
* 職業：無職
* 初期才能：ランダムで1個
* 潜在能力：開始時点では未確定
* 限界突破回数：0

種族進化、種族変更、転生は実装しない。

### 成長要素

* プレイヤーレベル
* 職業レベル
* 武器熟練度
* 魔法熟練度
* スキル熟練度
* 自由能力ポイント
* 才能
* 潜在能力
* 称号
* 限界突破

### レベル成長

序盤はレベルアップしやすく、終盤ほど必要経験値が増加する。

格上の敵から得られる経験値は増加し、格下の敵から得られる経験値は減少する。

才能や職業によって成長速度が異なる。

限界突破するたびに、さらなる成長が難しくなる。

単調な経験値稼ぎだけを強制する設計にはしないこと。

以前の基本8能力値を、以下の12能力値へ変更する。

| 能力値 | 主な効果 |
|---|---|
| 筋力 | 物理攻撃力・積載量 |
| 耐久 | 最大HP・物理防御力 |
| 魔力 | 魔法攻撃力・最大MP |
| 精神 | 魔法防御力・状態異常耐性 |
| 敏捷 | 移動・回避性能 |
| 器用 | 命中・クリティカル |
| 幸運 | 希少報酬・確率系能力 |
| 知力 | 魔法効率・スキル習得 |
| 生命力 | HP回復・回復効果 |
| 持久力 | スタミナ・疲労耐性 |
| 集中力 | 詠唱速度・詠唱妨害耐性 |
| 統率力 | 召喚獣・仲間NPCへの補正 |

さらに職業系統ごとの専用能力値を追加可能とする。

例：剣気、闘気、守護力、魔力制御、召喚力、信仰力、隠密力など。

能力値には成長上限を設定し、限界突破によって上限を解放する。

既存の8能力値のセーブデータは維持し、新しい4能力値のみ適切な初期値を追加すること。

## 第8章 才能・潜在能力

### 初期才能

全員がランダムで1個の才能を獲得する。

初期才能は再ログインやゲーム内の死亡によって再抽選されない。

### 後天性才能

冒険、戦闘、修行、特殊イベント、実績によって追加の才能を獲得できる。

才能には等級や枝分かれする進化先を設定可能とする。

### 潜在能力

以前のゲーム開始時に潜在能力を抽選・固定する方式は廃止する。

プレイヤーの行動、職業、戦闘スタイル、攻略実績などを記録し、それらによって潜在能力が形成される方式に変更する。

覚醒するまでは具体的な能力名や覚醒条件を公開しない。

低等級の初期才能でも、最終的に強くなれる設計とする。

## 第11章 スキルシステム

以下の習得方法をすべて採用する。

* レベルアップ
* スキルポイント
* 行動による発見
* 熟練度
* 魔導書
* 師匠
* ステージ攻略
* 特殊条件
* 才能覚醒

スキルごとにレベルと熟練度を管理する。

枝分かれ進化、スキル融合、覚醒、職業や才能による性能変化を実装する。

### スキル操作の重要変更

以前の「しゃがみ操作との組み合わせを使用しない」という仕様は撤回する。

ホットバーの同一アイテムに複数の技を割り当てる方式へ変更する。

| 操作 | 発動する技の基本例 |
|---|---|
| 通常使用 | 小技・小魔法 |
| ジャンプ中に使用 | 中技・中魔法 |
| ダッシュ中に使用 | 移動技 |
| しゃがみながら溜めて使用 | 大技・大魔法 |
| 長時間溜めて使用 | 奥義・超大魔法 |

ホットバー9枠×5操作で、理論上最大45種類の技を使い分けられることを目標とする。

魔法職だけでなく、戦士、弓使い、回復職などにも適用する。

操作が競合する場合の優先順位、チャージ判定、誤発動防止、キャンセル、クールタイムを設計する。

未習得の技は使用できない。

MPやスタミナが不足している場合は発動できない。

Switchのコントローラーで動作する既存操作のみを利用すること。

すべての操作判定が安定版Script APIで実現可能か確認し、困難なものは代替案を報告すること。無断で操作方式を削除しないこと。

### 強化失敗

強化に失敗した場合、消費するのは使用した素材のみとする。

ワールド内に一つしか存在しない特殊装備を実装する。

* 仲間への譲渡が可能。
* 装備自身が所有者を選ぶ。
* 使用することで固有能力が成長する。
* 所有者の職業や才能によって性能と進化先が変化する。
* 紛失しても特殊な方法で取り戻せる。
* 最初の入手者に永久固定しない。
* 複製を防止する。

## 第15章 報酬システム

ステージ攻略報酬はプレイヤーごとに個別抽選する。

* 希少度が高いほどドロップ率は低い。
* 超希少装備も存在する。
* 幸運や才能によって確率が変化する。
* ステージの難易度が高いほど豪華な報酬が得られる。
* 周回数に応じたドロップ率上昇を採用する。
* 周回補正には上限を設ける。

確率や上限値は設定データから変更可能とする。

世界唯一の装備が複数人に同時配布されないようにする。

## 第17章 魔神野口

魔神野口はゲーム開始時から圧倒的な強さを持つ。

三魔将全員が力を合わせても敵わない存在とする。

ステージ100において最終決戦を行う。

固有能力は以下の6種類とする。

1. 透明化：姿を消す。
2. 無敵：一定時間ダメージを無効化する。
3. テレポート：戦闘エリア内を瞬間移動する。
4. 無力化：勇者の能力やスキルを一時的に封じる。
5. 回復：自身のHPを回復する。
6. 即死：勇者をゲーム内で即座に戦闘不能にする。

複数の形態と特殊演出を用意する。

強力な能力には攻略可能な対抗手段を設定する。

## 第18章 真の黒幕・女王ホープ

以下の情報は本編クリアまでプレイヤーに明かさないこと。

ホープこそがパラレルワールドを作り出した真の黒幕である。

本当の目的は、4人を高校から卒業させないことである。

大学生になった4人をパラレルワールドに閉じ込めるため、魔神野口討伐と富里王国復興の冒険を仕組んでいた。

魔神野口を倒して富里王国へ帰還すると、ホープが真実を明かす。

セリフ例：

「魔神野口の討伐、お疲れ様でしたぁ〜」

「でもぉ〜、元の世界には帰れませぇ〜ん」

「実はこの世界を作ったのは私でしたぁ〜」

「皆さんに高校を卒業してほしくなかったんですよぉ〜」

その後、裏ボスであるホープとの決戦が始まる。

### ホープの固有能力

* 世界創造：戦闘エリアの地形変化と魔物の生成。
* 時間逆行：HPや戦闘状況を巻き戻す。
* 卒業拒絶：勇者の能力を一時的に初期状態へ戻す。
* 記憶再現：過去に討伐したボスを再召喚する。

卒業拒絶によって実際のセーブデータや成長記録を削除しない。

ホープを倒すことで真のエンディングを迎える。

ホープ戦は本編100ステージとは別のクリア後専用コンテンツとして管理する。

## 第19章 マルチプレイ・復活

1～4人で遊べるようにする。

4人全員が揃っていなくてもストーリーを進行できる。

不足人数は仲間NPCによって補完可能とする。

NPCは攻撃、防御、回復、支援などを自律的に行う。

参加人数やNPC数に応じて敵の強さやギミックを調整する。

ゲーム全体の難易度自動調整とは区別すること。

### 戦闘不能・復活

* 仲間による救助
* 蘇生魔法
* 復活アイテム
* ステージ別の復活回数制限
* 戦闘不能中の観戦
* 戦闘不能中の限定的な仲間支援

全滅時のペナルティはステージ難易度によって変化する。

## 第20章 その他のRPGシステム

### 経済

通貨は金貨のみとする。

複数通貨や変動経済は実装しない。

### 冒険者ギルド

冒険者ランク、昇格試験、依頼、ランク別ステージ解放、専用商品、専用報酬を実装する。

ただし、冒険者ランクによる制限はメインストーリーの進行方式と矛盾しないように設定する。

### クエスト

メイン、サブ、ランダム依頼、隠し、連続、職業専用、才能専用、称号専用クエストを採用する。

ランダム依頼を生成してもステージマップ自体はランダム生成しないこと。

### 称号

実績、能力値上昇、固有能力、職業・スキル解放、世界唯一の称号を採用する。

### NPC

名前、性格、会話、好感度、専用クエスト、師匠からのスキル習得を採用する。

NPCの自律的な生活や独立した成長シミュレーションは実装しない。

### 召喚

一部の職業のみ使用可能とする。

野生モンスターの捕獲、従魔の個別育成、繁殖は実装しない。

召喚獣の強さは召喚者の能力値、才能、職業、スキルによって決まる。

同時召喚数は少数に制限する。

### アイテム管理

インベントリ、個人倉庫、共有倉庫、重量、分類、自動整理、アイテム保護、一括売却を採用する。

### 移動

徒歩、馬、特殊乗り物、ファストトラベル、転移魔法、帰還アイテム、馬車、飛行船を採用する。

ただし、メインステージの移動は専用ステージへのテレポート方式を優先する。

### 特殊自然現象

満月、赤い月、流星群、皆既日食などの特殊現象を採用する。

通常の昼夜や天候による常時能力変化は採用しない。

### Minecraft標準要素

建築、採掘、ブロック破壊、農業などは大幅に制限する。

通常のサバイバルゲームではなく、完全RPG型とする。

## 第21章 グラフィック・音楽・演出

グラフィックはMinecraft標準風を維持する。

追加武器、防具、魔物、魔法、建築物もMinecraftの世界に自然になじむデザインにする。

以下の演出を採用する。

* 地域・ステージ専用BGM
* ボス専用BGM
* 魔法・スキル専用効果音
* カメラ演出
* 字幕
* 暗転
* ボス登場演出
* 形態変化演出
* 職業進化演出
* 才能覚醒演出
* 限界突破演出
* 王国復興演出

音源はオリジナルまたは利用許諾のあるものを使用する。

## 第22章 HUD・UI

以下の情報を表示できるようにする。

* HP
* MP
* スタミナ
* レベル
* 経験値
* 職業
* スキルクールタイム
* 仲間のHP・MP・状態異常
* 敵のHP・レベル・属性・弱点
* クエスト進行
* ステージ攻略状況

Switch版で利用可能なアクションバー、ボスバー、スコアボード、フォーム、アイテムなどを活用する。

非対応の独自GUIや入力機能を前提にしないこと。

## 第23章 セーブ・データ管理

以下のデータを確実に保存する。

### 個人データ

レベル、経験値、12能力値、職業、職業履歴、才能、潜在能力の形成状況、熟練度、スキル、操作割り当て、装備、金貨、称号、冒険者ランク、クエスト、倉庫、NPC好感度。

### ワールド共有データ

ストーリー進行、章進行、ステージ解放状況、ステージ攻略記録、王国復興状況、移住済み住民、建設済み施設、ボス討伐記録、唯一装備・称号の管理、特殊イベント。

自動保存、途中再開、データ移行、破損検知、可能な範囲での復旧処理を実装する。

アドオン内部で実現できないバックアップは外部手順を用意する。

## 第24章 クリア後

* クリア後限定スキル

## 第27章 開発時の絶対条件

* Minecraft統合版専用。
* Java版MODとして制作しない。
* Switchからのプレイを最優先する。
* PC版統合版およびRealms経由での導入を想定する。
* 実在する安定版Script APIのみを使用する。
* 対象のMinecraftバージョンとAPIバージョンを明記する。
* 既存パックのUUIDを維持する。
* 既存セーブデータを無断で削除しない。
* データ移行前にはバックアップを推奨する。
* 既存機能を無断で削除・簡略化しない。
* 数値、職業、スキル、敵、報酬などはデータ駆動型にする。
* 大量の毎tick処理を避ける。
* プレイヤーがいないステージの処理を停止する。
* NPCや召喚獣の同時稼働数を制限する。
* 大規模建築の配置処理は分散する。
* 実現困難な仕様は勝手に変更せず、理由と代替案を報告する。
* 実際に動作確認していないものを動作確認済みと報告しない。
* 実機で検証できない機能は未検証と明記する。

この仕様書をプロジェクト内のMASTER_SPEC.mdなどに保存し、今後の開発でも必ず参照すること。

追加決定や仕様変更は別途変更履歴に記録すること。
