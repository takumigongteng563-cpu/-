# 引き継ぎ資料（第3弾へ）

第3弾以降の開発者（人間・AI問わず）が最初に読む資料です。v0.2.0（第2弾まで）時点の内容です。

## 1. 絶対に守ること

| 項目 | 理由 |
|---|---|
| `packs/BP/manifest.json` の **header.uuid を変更しない**（RP も同様） | 動的プロパティはビヘイビアーパックごとに保存される。変えると全セーブが読めなくなる |
| `config.js` の `KEY_PREFIX`（`mnq`）・`NAMESPACE`（`noguchi`）・`ITEM_IDS` を変更しない | 保存キー・アイテムIDに直結する |
| `PLAYER_UID_PROPERTY`（`mnq:uid`）を変更しない | プレイヤーと個人データを結ぶ唯一の鍵 |
| 保存データの**既存項目を削除・改名しない** | 古いデータの読み込み時に失われる。不要になった項目は残したまま使わない |
| `content/` の**公開済みIDを変更・削除しない** | 職業・スキル等のIDは保存データに書き込まれる |
| データの意味や型を変えるときは**スキーマバージョンを上げて移行処理を書く** | 下記「4. データ構造の変更手順」 |
| バージョンを上げるときは header.version・modules の version・相互依存の version を**すべて同じ値に** | `npm run validate` が不一致を検出する |
| `@minecraft/server` のバージョンを上げるときは `package.json` の devDependencies も同じ値にして `npm run typecheck` | manifest と型定義の一致は validate が検査する |
| 仮実装を完成済みと書かない／未検証を検証済みと書かない | 指示書の条件 |
| 能力値・派生能力値の**合計を保存データに直接足さない**（`computed` は計算結果の写し） | 合計は毎回 `computeStats` でゼロから計算する設計。直接足すと再計算で消える・重複する |
| 初期才能を**再抽選する処理を作らない** | 指示書：再ログイン・死亡による引き直し不可 |
| 経験値は必ず `grantExp` 経由で付与し、報酬ごとに `key` を付ける | 二重付与防止と、レベルアップ処理（ポイント・成長・才能判定）を通すため |
| `tests/fixtures/v1-state.json` を再生成しない | 第1弾の実データからの更新を検証する唯一の資料 |

## 2. 全体構成

```
main.js ── イベント購読（worldLoad / playerSpawn / playerLeave / itemUse / shutdown）
   │         起動時に app.js の createApp() で全サービスを作り ctx に入れる
   │
   ├─ ctx（core/context.js）… 起動後に各サービスが入る
   │    ├─ worldService   … ワールド共有データ（"world"）と索引（"index"）
   │    ├─ playerService  … 個人データ（"p.<uid>"）とセッション
   │    ├─ partyService   … 人数・倍率表・NPC補完の差し込み口
   │    ├─ progression    … 経験値・レベル・能力ポイント・限界突破（第2弾）
   │    ├─ stats          … 能力値の再計算・一時効果（第2弾）
   │    ├─ talents        … 才能の抽選・獲得・進化・潜在能力（第2弾）
   │    ├─ actions        … 行動の記録・フラグ（第2弾）
   │    └─ vitals         … HP・MP・スタミナ（第2弾）
   │
   ├─ storage/saveManager   … 自動保存（200tickごと・最大2件）
   ├─ rules/actionGuard     … 行動制限
   ├─ actions/combatHooks   … 命中・討伐・被ダメージの記録、暫定の討伐経験値（第2弾）
   ├─ vitals/vitalsRuntime  … HP連動・自然回復・スタミナ・移動距離（第2弾）
   ├─ hud/hud               … アクションバーHUD（第2弾）
   ├─ fx/effects            … レベルアップ等の演出（core/eventBus のイベントを受ける）（第2弾）
   ├─ ui/menu               … メニュー
   └─ admin/scriptEvents    … 管理コマンド

内部イベント（core/eventBus.js）：levelUp / expGained / talentAcquired / talentEvolved /
  potentialAwakened / limitBreak / statsChanged / vitalsChanged
  → 演出・HUD・将来の実績やログ機能は on("levelUp", ...) で受け取れる

保存の層：
  サービス（world/playerService）
    → RecordManager（キャッシュ・dirty管理・移行・補完）
      → ChunkedStore（分割・A/B二重化・チェックサム）
        → worldBackend（world.get/setDynamicProperty）
```

### 保存キー（ワールドの動的プロパティ）

| キー | 内容 |
|---|---|
| `mnq:<名前>:m` | 管理情報（どちらの枠が最新か、各枠のチャンク数・長さ・チェックサム・世代） |
| `mnq:<名前>:a0`, `a1`… / `b0`, `b1`… | 本体（ASCII化した JSON を 16,000 文字ずつ分割） |

`<名前>` は `world`（共有データ）、`index`（索引）、`p.<uid>`（個人データ）、`q:<元の名前>:<時刻>`（破損データの退避）。
本体 JSON は `{ k: 種別, s: スキーマ版, g: 世代, t: 保存時刻, d: データ }` の形です。

プレイヤー本人の動的プロパティには `mnq:uid`（識別ID）のみを保存しています。

## 3. データの読み書きの方法（後続の開発で使う API）

```js
import { ctx } from "./core/context.js";

// 読む
const d = ctx.playerService.dataFor(player.id);

// 書く（通常：自動保存に任せる）
ctx.playerService.update(player.id, (d) => { d.exp += 10; });

// 書く（重要：即時保存。レベルアップ・転職・レア入手など）
ctx.playerService.update(player.id, (d) => { d.level++; }, { important: true });

// ワールド共有データ
ctx.worldService.updateWorld((w) => { w.bosses.defeated["sumire"] = { defeatedAt: Date.now(), count: 1 }; }, { important: true });

// 不在プレイヤーのデータを参照（読み取り専用コピー）
const offline = ctx.playerService.peekOffline(uid);

// ---- 第2弾で追加 ----
// 経験値（後続のボス・ダンジョン・クエスト・試練から）
ctx.progression.grantExp(player.id, 500, { source: "boss", key: `boss:${bossEntity.id}` });
ctx.progression.grantExp(player.id, 300, { source: "quest", key: "quest:main_ch1", once: true });

// 行動の記録（後天性才能・潜在能力・進化の条件になる）
ctx.actions.record(player.id, "magic.cast");          // 魔法を使った
ctx.actions.record(player.id, "heal.amount", 35);     // 回復量
ctx.actions.record(player.id, "protect.ally");        // 仲間を守った
ctx.actions.setFlag(player.id, "spirit_resonance");   // 特殊イベント・試練の達成

// スキル使用の共通処理（MP・スタミナが足りなければ false、何も消費しない）
if (!ctx.vitals.trySpend(player.id, { mp: 20, stamina: 5 })) { /* 使用不可 */ }

// 一時効果（同じ id は上書き＝重ねがけ不可）
ctx.stats.addBuff(player.id, { id: "potion_str", name: "力の薬", stats: { flat: { str: 5 } }, durationTicks: 1200 });

// 能力値・派生能力値の参照（計算済みの値）
const d = ctx.playerService.dataFor(player.id);
d.computed.primary.str;       // 筋力
d.computed.derived.physAtk;   // 物理攻撃力
d.computed.elements.fire;     // 火属性耐性(%)
ctx.stats.inspect(player.id); // 層ごとの内訳つき（表示用）
```

- `update` は保護モード（新しい版のデータ等）やオフラインのプレイヤーに対しては `false` を返し、何もしません
- **毎tick `update` を呼んでも保存領域への書き込みは発生しません**（メモリ上の変更＋dirty 印のみ）。ただし処理負荷のため、毎tickの処理自体を避けてください
- 世界唯一の装備・称号は、必ず `updateWorld(..., { important: true })` で所有者を記録してから本人に付与してください（同時取得による重複を防ぐため）

## 4. データ構造の変更手順

### 項目を追加するだけの場合
`player/playerSchema.js`（または `world/worldSchema.js`）の `playerTemplate()` に既定値付きで追加するだけで、既存データには読み込み時に自動で補われます。バージョンを上げる必要はありません。

### 意味・型・配置を変える場合
1. `config.js` の `PLAYER_SCHEMA_VERSION` を +1（例：1 → 2）
2. `player/playerMigrations.js` に `1: (d) => { ...変換...; return d; }` を追加（キーは「変換前のバージョン」）
3. `tests/` に「v1 のデータが v2 に正しく変換される」テストを追加
4. `npm run check`

読み込み時は `破損検知 → 復旧 → 移行（v1→v2→…） → 欠損補完` の順で処理されます。
移行に失敗したデータは保護モード（読み取り専用）になり、上書きされません。

## 5. コンテンツ（職業・スキル・装備…）の追加方法

`content/` にレジストリを置き、定義を登録する方式です。

```js
// content/jobs.js に追加する例
export const jobs = new Registry("職業").registerAll([
  { id: "unemployed", name: "無職", tier: 0, maxLevel: 10, description: "…" },
  { id: "swordsman", name: "剣士", tier: 1, maxLevel: 50, description: "…", requires: { job: "unemployed", level: 10 } },
]);
```

- 数百～千件規模になる場合は `content/jobs/` のようにフォルダを分け、系統ごとのファイルから `registerAll` してください
- 新しい種類（スキル・装備・モンスター等）は `content/skills.js` のように新規作成し、`content/index.js` に追記
- ID の重複は自動で拒否され、エラーログに出ます

## 6. メニューページの追加方法

`ui/pages/` に `{ id, label, icon, async open(player) }` を持つオブジェクトを作り、`ui/menu.js` の `PAGES` に加えます。
`open` は `"back"`（メインメニューへ戻る）か `"close"` を返します。情報表示だけなら `showInfoPage()` が使えます。
フォームは必ず `showForm()` 経由で表示してください（チャット中の再試行・エラー処理が入っています）。

## 7. 処理負荷のルール

- `system.runInterval` を間隔1（毎tick）で使わない。必要なら `core/scheduler.js` の `every()` で20tick以上を基本にする
- プレイヤーが多い処理は1回の実行で全員を処理せず、順番に少しずつ処理する（自動保存と同じ方式）
- 動的プロパティを直接読み書きしない（必ず各サービス経由）
- イベント購読は `core/events.js` の `subscribe()` を使う（エラー隔離）
- `before` 系イベントの中では書き込み系APIが使えないため、`system.run()` で次のtickに回す（`rules/actionGuard.js` 参照）

## 8. テスト

```bash
cd minecraft
npm install
npm run check
```

- 純粋ロジック（storage / player / world / party / content）は `tests/*.test.mjs` で単体テスト
- `tests/integration/session.mjs` は `main.js` を模擬エンジン（`tests/mock/`）上で動かすシナリオ。新しいイベントや API を使ったら、模擬エンジンにも最小限の実装を追加してください
- 模擬エンジンは実機の完全な再現ではありません。**実機確認は [動作確認手順](動作確認手順.md) で別途必要**です

## 9. 第3弾（職業・転職）の実装の入口

第2弾は職業の受け皿を用意してあります。

| やること | 場所 |
|---|---|
| 職業の定義を追加（`stats` / `derived` / `growth` を書けば能力値・成長率に自動で反映） | `content/jobs.js`（`Registry`）。数百件になるなら `content/jobs/` に分割 |
| 職業補正は層「職業」として内訳に表示される | `stats/statCalc.js` の `collectModifiers` が `data.job.current` の定義を読む（実装済み） |
| 職業レベル・経験値 | 保存先 `data.job.levels[jobId] = { level, exp }`（第1弾から用意済み）。経験値は `grantExp` の中で職業経験値も加算するように拡張する |
| 転職履歴 | `data.job.history`、解放済み職業 `data.job.unlocked`（第1弾から用意済み） |
| 才能の職業適性 | 才能定義の `jobAptitude: { swordsman: 0.1 }`。キーは職業ID（または職業の系統タグ）と一致させる。転職条件・職業経験値の倍率に使う想定 |
| 転職条件 | 才能の条件判定 `talents/conditions.js` の `checkAll` をそのまま使える（レベル・行動回数・才能・フラグ） |
| メニュー | `ui/pages/job.js` を拡張（「今後実装予定」表示を外す） |
| データ構造の変更 | 意味を変える場合は `PLAYER_SCHEMA_VERSION` を 3 にして `playerMigrations.js` に `2: (d) => …` を追加 |

## 10. 実機確認が必要な事項

次の開発を始める前に、実機で確認してください（結果によって設計の修正が必要になる可能性があります）。

### 第1弾から引き続き
1. 冒険者の書で `world.afterEvents.itemUse` が発火するか（Switch の ZL を含む）
2. `system.beforeEvents.shutdown` の中で `world.setDynamicProperty` が成功するか
3. `playerInteractWithBlock` の取り消しで、ブロックの設置が実際に止まるか
4. Realms 上で4人同時プレイ時、自動保存による引っかかり（ラグ）が体感できないか
5. Realms への「ワールドを置き換える」でアドオンと保存データが正しく引き継がれるか

### 第2弾で追加
6. アクションバーの2行表示が Switch（携帯モード含む）で読めるか。ほかの表示と重ならないか
7. `entityHitEntity` / `projectileHitEntity` / `entityDie` / `entityHurt` / `entityHealthChanged` が想定どおりの順序・回数で発火するか（特に討伐時の `damageSource.damagingEntity` が矢の場合に射手になるか）
8. `matches({ families: ["monster"] })` でバニラの敵対モブが判定できるか（ゾンビピグリン・エンダーマンなど中立モブの扱い）
9. 効果音 `random.levelup` `random.totem` `random.orb` `random.anvil_use` `ambient.weather.thunder`、パーティクル `minecraft:villager_happy` `minecraft:totem_particle` が実機で出るか
10. 鈍化の付与（`addEffect("slowness")`）がスタミナ切れの演出として適切か
11. HP の自然回復（`setCurrentValue`）がバニラの回復と干渉しないか
